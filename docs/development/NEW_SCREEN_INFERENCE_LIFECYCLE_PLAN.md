# New Screen Inference Lifecycle Plan

## 1. Purpose

This document defines the feature contract for creating a new screen from user-provided client materials.

The feature starts in the Web client. A user drops related materials into the screen, waits while screen inference runs, reviews the rendered UI result, and then approves the result for DB registration.

The inference model keeps the existing logical layer names:

```text
Understand -> Compose -> Revise
```

`Compose` remains the product and code vocabulary. Do not rename this layer to `Design`.

This document does not replace [PIPELINE_STAGE_PROTOCOL.md](/Users/plusx/Documents/rnd-screen-generator/docs/development/PIPELINE_STAGE_PROTOCOL.md). That document remains the source of truth for executable pipeline stage order and package ownership.

## 2. User Data Lifecycle

The new screen flow treats user input as the start of a persisted generation lifecycle.

```text
Client DnD input
-> source artifact registration
-> screen-generation pipeline run
-> layer progress visible in Web UI
-> rendered UI preview
-> user review
-> approval
-> final-result.json -> render_* DB registration
-> Web/Workbench reads the registered screen from DB
```

The Web UI must show a rendered UI result, not only a text summary. The preview source is the RenderTree generated by the pipeline.

The final generation source of truth before approval is `final-result.json`. After approval, the source of truth for app browsing is the relational screen read model in the `render_*` tables.

## 3. Current Baseline

The existing screen-generation pipeline already has the right logical structure.

| Layer | Pipeline stages | Existing artifacts |
|---|---|---|
| `understand` | `read-source`, `parse-source`, `derive-screen-intent` | `source-spec.json`, `screen-intent.json` |
| `compose` | `plan-composition`, `derive-decoration-plan`, `select-pattern`, `generate-render-tree`, `propose-components` | `composition-plan.json`, `decoration-plan.json`, `pattern-selection.json`, `agent-result.json`, `component-proposal.json` |
| `revise` | `validate-render-tree`, `review-quality`, `revise-render-tree-if-invalid`, `validate-render-tree-after-revision`, `write-artifacts` | `validation-report.json`, `quality-review.json`, `final-result.json`, `pipeline-result.json` |

The current smoke explorer can browse stored runs and render `final-result.json`. It does not yet start a run from DnD input, stream or poll live progress, or gate DB registration behind user approval.

## 4. UX Contract

The user must be able to see the current inference layer while waiting.

Required states:

| State | Meaning |
|---|---|
| `queued` | The input is accepted but inference has not started. |
| `running` | At least one pipeline layer is active. |
| `waiting-review` | A rendered result is ready for user review. |
| `approved` | The user approved the generated result. |
| `applying` | The approved result is being registered in DB. |
| `applied` | DB registration completed. |
| `failed` | The run stopped with an error. |

Each layer must expose its own status:

| Layer status | Meaning |
|---|---|
| `pending` | The layer has not started. |
| `running` | At least one stage in the layer is active. |
| `completed` | The layer finished and its reviewable output is available. |
| `failed` | The layer failed or produced blocking diagnostics. |
| `skipped` | The layer was not executed because an earlier condition stopped the run. |

The UI should present the layers in this order:

```text
Understand
Compose
Revise
```

At minimum, the UI must show:

- current layer
- completed layers
- failed layer and error summary
- final rendered preview when available
- approval action after reviewable output is available

## 5. Layer Review Contract

Each layer should have a user-reviewable snapshot.

| Layer | Reviewable content | Preview expectation |
|---|---|---|
| `understand` | Source summary, screen intent, primary user action, content priority, deferred/preserved/summarized source refs | No rendered UI required. |
| `compose` | Composition plan, decoration plan, selected patterns, component proposal summary, generated RenderTree draft | Rendered draft UI should be available when `generate-render-tree` succeeds. |
| `revise` | Validation report, quality review, revision decision, revised RenderTree if revision ran | Final rendered UI must be available. |

The `compose` preview can use the RenderTree inside `agent-result.payload.renderTree`. For a stable UI contract, the pipeline should eventually expose a dedicated draft preview pointer instead of requiring Web to inspect the raw agent result envelope.

Suggested future artifact:

```text
artifacts/draft-result.json
```

`draft-result.json` should contain the RenderTree candidate produced before Revise. `final-result.json` remains the reviewed and revision-aware RenderTree.

## 6. Status Artifact Contract

The Web client needs a stable way to read progress.

Preferred contract:

```text
data/runs/screen-generation/<run-id>/
  manifest.json
  status.json
  artifacts/
    ...
```

Suggested `status.json` shape:

```ts
type ScreenInferenceRunStatus = {
  schemaVersion: "screen-inference-run-status.v0.1";
  runId: string;
  status: "queued" | "running" | "waiting-review" | "approved" | "applying" | "applied" | "failed";
  currentLayer?: "understand" | "compose" | "revise";
  createdAt: string;
  updatedAt: string;
  layers: Array<{
    layer: "understand" | "compose" | "revise";
    label: "Understand" | "Compose" | "Revise";
    status: "pending" | "running" | "completed" | "failed" | "skipped";
    startedAt?: string;
    completedAt?: string;
    stages: string[];
    artifacts: string[];
    previewArtifact?: string;
    summary?: {
      title?: string;
      description?: string;
      errorCount?: number;
      warningCount?: number;
    };
  }>;
  error?: {
    code: string;
    message: string;
  };
};
```

The DTO should live in `@cx/schema`. `@cx/pipeline` should write or emit it because pipeline owns stage execution and artifact write.

## 8. API Surface Direction

The Web feature should use server-owned APIs. Browser components must not import `@cx/pipeline` or `@cx/agent` directly.

Suggested routes:

| Route | Responsibility |
|---|---|
| `POST /api/screen-inference/runs` | Accept uploaded materials or a registered source artifact reference, create a run, start pipeline execution. |
| `GET /api/screen-inference/runs/:runId` | Return manifest and `status.json`. |
| `GET /api/screen-inference/runs/:runId/artifacts/:artifactName` | Return an allowed artifact by manifest pointer. |
| `POST /api/screen-inference/runs/:runId/approve` | Mark the reviewed run as approved and start DB registration. |
| `POST /api/screen-inference/runs/:runId/apply` | Register approved `final-result.json` into the screen DB read model. |

The exact transport can be polling first. SSE or a worker queue can be added later without changing the status DTO.

## 8.1 New Screen Tab MVP Data Contract

The new screen tab must reuse the current Web tab structure. Do not invent a separate navigation or layout shell for MVP.

Required UI structure:

```text
Left navigation sidebar rail
-> Run | rerun
-> uploaded screenId list

Center top
-> inference status stepper: Understand -> Compose -> Revise
-> current status / error / completion summary
-> save/apply action

Center
-> rendered screen UI preview

Right
-> validation / quality summary
```

The UI can change later, so MVP implementation should keep the data endpoints simple and obvious.

Endpoint-to-UI mapping:

| UI area | Endpoint | Data consumed |
|---|---|---|
| Left rail upload source list | `POST /api/screen-inference/sources` | returns `source.importId`, `source.batchId`, `source.screenId`, `source.path` |
| Left rail run/rerun action | `POST /api/screen-inference/runs` | returns `runId`, `statusUrl` |
| Left rail uploaded screenId | local state first, later `GET /api/screen-inference/sources` if persisted browsing is needed | `screenId`, `source.path`, latest `runId` |
| Center top stepper | `GET /api/screen-inference/runs/:runId` | `status.currentLayer`, `status.layers[]` |
| Center top status text | `GET /api/screen-inference/runs/:runId` | `status.status`, `status.error`, `manifest.summary` |
| Center preview | `GET /api/screen-inference/runs/:runId/artifacts/final-result.json` | `RenderTreeContract` rendered through `@cx/renderer` |
| Right validation summary | `GET /api/screen-inference/runs/:runId/artifacts/validation-report.json` | validation `ok`, `summary`, `issues[]` |
| Right quality summary | `GET /api/screen-inference/runs/:runId/artifacts/quality-review.json` | quality scores, findings, summary |
| Save/apply action | `POST /api/screen-inference/runs/:runId/apply` | apply result, registered screen tree or diagnostics |

MVP tab state should be small:

```ts
type NewScreenTabState = {
  selectedRunId?: string;
  selectedSourcePath?: string;
  selectedScreenId?: string;
  sourceItems: Array<{
    batchId: string;
    importId: string;
    latestRunId?: string;
    path: string;
    screenId: string;
  }>;
};
```

`Run` starts a new pipeline run for the selected source. `rerun` starts another run for the same `source.path` and records the previous `runId` in request metadata or tags. MVP rerun does not resume a Claude session.

The center preview must not read DB state before apply. Before approval, it renders the run artifact. After apply succeeds, Web can reload the registered screen from the existing screen DB endpoints.

```text
│ Left navigation rail     │ Center top                               │ Right review panel   │
│                          │ Understand -> Compose -> Revise          │                      │
│ Run | rerun              │ status / error / completion / save       │ validation summary   │
│ uploaded screenId list   ├──────────────────────────────────────────┤ quality summary      │
│                          │                                          │ issue highlights     │
```

MVP screen states:

| State | Left rail | Center top | Center preview | Right panel |
|---|---|---|---|---|
| Empty | DnD prompt, no selected source | all layers pending | no screen selected | no validation |
| Uploaded | selected `screenId`, `Run` enabled | `queued` | no preview | no validation |
| Running | selected `screenId`, rerun disabled | current layer from `status.json` | loading/empty preview | pending validation |
| Waiting review | selected latest run, `rerun` enabled | all layers completed, `save/apply` enabled | rendered `final-result.json` | validation and quality summaries |
| Failed | selected failed run, `rerun` enabled | failed layer and error | partial or empty preview | error diagnostics when available |
| Applied | selected applied run | `applied` | registered DB screen or final preview | apply diagnostics and registered screen id |

## 8.2 MVP Rollout Plan

Rollouts should ship in small vertical slices. UI polish and layer-level review snapshots are deferred until the main data lifecycle works.

### Rollout 1 - DnD Source Intake

Goal: a user can drop a Markdown source and see the uploaded `screenId` in the left rail.

Scope:

- Add `POST /api/screen-inference/sources`.
- Save files to `data/client-imports/{importId}/{batchId}/{screenId}.md`.
- Add the new screen tab shell by reusing the existing Web tab layout.
- Show uploaded `screenId`, `source.path`, and basic upload errors.

Done when:

- Dropping a valid `.md` creates a file under `data/client-imports`.
- The left rail lists the uploaded `screenId`.
- The center preview remains empty until a run starts.

### Rollout 2 - Run Creation And Status Polling

Goal: a user can start inference and watch `Understand -> Compose -> Revise` progress.

Scope:

- Add `POST /api/screen-inference/runs`.
- Add `GET /api/screen-inference/runs/:runId`.
- Add pipeline `status.json` writing or an equivalent status adapter.
- Poll status from the Web tab.
- Show active layer, completed layers, failed state, and completion state.

Done when:

- Clicking `Run` starts `runPipeline("screen-generation")`.
- The center top stepper updates from polling.
- Completed runs expose `manifest.json` and final artifact pointers.

### Rollout 3 - Final Review And Rerun

Goal: a user can inspect the rendered final result and request a new run.

Scope:

- Add artifact read endpoint for allowed final review artifacts.
- Render `final-result.json` in the center preview.
- Show validation and quality summaries in the right panel.
- Add `rerun` action that creates a new run for the same `source.path`.
- Keep rerun as a new session/new run in MVP.

Done when:

- A completed run renders the generated UI.
- Validation and quality summaries are visible.
- Rerun creates a new `runId` without mutating the previous run.

### Rollout 4 - Approved DB Apply

Goal: a user can save an approved final result into the screen DB read model.

Scope:

- Add `POST /api/screen-inference/runs/:runId/apply`.
- Validate `final-result.json` before apply.
- Project/decompose the RenderTree into `render_*` rows.
- Upsert rows through the Web screen DB facade.
- Reload the registered screen through existing screen DB endpoints.

Done when:

- Clicking `save/apply` registers a new screen.
- The registered screen can be loaded through `/api/screens/*`.
- The apply path does not call Claude or reinterpret the source.

### Rollout 5 - Layer Review Snapshots

Goal: completed layers expose reviewable summaries without requiring Web to parse `trace.json`.

Scope:

- Add layer snapshot artifacts.
- Add optional `draft-result.json` for Compose preview.
- Show Understand and Compose summaries in the UI.

Done when:

- Users can inspect each completed layer.
- Compose draft preview is available without reading `agent-result.payload.renderTree`.

This rollout is intentionally after the MVP lifecycle. It should not block DnD, polling, final review, rerun, or DB apply.

## 9. Approval And DB Registration

Approval is a separate lifecycle step after inference. The pipeline should not automatically register a generated screen into DB.

Approved registration should follow this rule:

```text
final-result.json
-> decompose/project RenderTree into screen, region, area, component rows
-> upsert into render_* tables
-> reload through screen DB loader
-> render through @cx/renderer
```

The apply step must not:

- reinterpret the source
- regenerate the screen
- change layout decisions
- run Claude
- bypass validation diagnostics
- write old local table JSON as the approval path

The direct `final-result.json -> render_*` apply path is still pending in the current repository. This feature should treat it as a required implementation phase, not as an existing capability.

MVP route example:

```ts
// apps/web/src/app/api/screen-inference/sources/route.ts
import { mkdir, writeFile } from "node:fs/promises";
import path from "node:path";
import { NextResponse } from "next/server";

const CLIENT_IMPORT_ROOT = path.join(process.cwd(), "data/client-imports");

export async function POST(request: Request) {
  const formData = await request.formData();
  const file = formData.get("file");
  const importId = sanitizePathPart(String(formData.get("importId") ?? "web-upload"));
  const batchId = sanitizePathPart(String(formData.get("batchId") ?? createBatchId()));

  if (!(file instanceof File)) {
    return NextResponse.json({ error: "Missing file." }, { status: 400 });
  }
  if (!file.name.endsWith(".md")) {
    return NextResponse.json({ error: "MVP only accepts Markdown source files." }, { status: 400 });
  }

  const screenId = sanitizePathPart(file.name.replace(/\.md$/i, ""));
  const targetDir = path.join(CLIENT_IMPORT_ROOT, importId, batchId);
  const targetPath = path.join(targetDir, `${screenId}.md`);

  await mkdir(targetDir, { recursive: true });
  await writeFile(targetPath, await file.text(), "utf8");

  return NextResponse.json({
    source: {
      importId,
      batchId,
      screenId,
      path: path.relative(process.cwd(), targetPath),
      type: "file",
    },
  });
}

function createBatchId() {
  return new Date().toISOString().slice(0, 10).replaceAll("-", "");
}

function sanitizePathPart(value: string) {
  return value.replace(/[^a-zA-Z0-9._-]/g, "_").slice(0, 80);
}
```

```tsx
type UploadedSource = {
```

### Phase B - MVP Run Creation And Status Polling

Run creation should accept a `source.path` that already points to `data/client-imports/...`.

Route example:

```ts
// apps/web/src/app/api/screen-inference/runs/route.ts
import { runPipeline } from "@cx/pipeline";
import { NextResponse } from "next/server";

export async function POST(request: Request) {
  const body = (await request.json()) as {
    runId?: string;
    source?: { path?: string };
    useAI?: boolean;
  };

  if (!body.source?.path?.startsWith("data/client-imports/")) {
    return NextResponse.json({ error: "source.path must be under data/client-imports/." }, { status: 400 });
  }

  const runPromise = runPipeline("screen-generation", {
    agentMode: body.useAI ? "claude-local-first" : "fake",
    runId: body.runId,
    source: {
      path: body.source.path,
      type: "file",
    },
    tags: ["web-new-screen"],
  });

  // MVP note: use a worker/queue when moving beyond local dev.
  void runPromise.catch((error) => {
    console.error(error instanceof Error ? error.message : error);
  });

  return NextResponse.json({
    runId: body.runId,
    statusUrl: body.runId ? `/api/screen-inference/runs/${body.runId}` : undefined,
  }, { status: 202 });
}
```

The route should return a deterministic `runId` in MVP. If the client does not provide one, the server should create one before calling `runPipeline()` so polling can start immediately.

Status polling route example:

```ts
// apps/web/src/app/api/screen-inference/runs/[runId]/route.ts
import { readFile } from "node:fs/promises";
import path from "node:path";
import { NextResponse } from "next/server";

type RouteContext = {
  params: Promise<{ runId: string }>;
};

export async function GET(_request: Request, context: RouteContext) {
  const { runId } = await context.params;
  const runDir = path.join(process.cwd(), "data/runs/screen-generation", runId);

  const status = await readOptionalJson(path.join(runDir, "status.json"));
  const manifest = await readOptionalJson(path.join(runDir, "manifest.json"));

  return NextResponse.json({
    manifest,
    status: status ?? {
      currentLayer: "understand",
      layers: [],
      runId,
      schemaVersion: "screen-inference-run-status.v0.1",
      status: "queued",
    },
  });
}

async function readOptionalJson(filePath: string) {
  try {
    return JSON.parse(await readFile(filePath, "utf8")) as unknown;
  } catch {
    return undefined;
  }
}
```

Polling client example:

```tsx
type RunStatusResponse = {
  status: {
    currentLayer?: "understand" | "compose" | "revise";
    runId: string;
    status: "queued" | "running" | "waiting-review" | "failed" | "applied";
  };
};

async function pollRun(runId: string, onStatus: (status: RunStatusResponse["status"]) => void) {
  const timer = window.setInterval(async () => {
    const response = await fetch(`/api/screen-inference/runs/${runId}`);
    const body = (await response.json()) as RunStatusResponse;
    onStatus(body.status);

    if (["waiting-review", "failed", "applied"].includes(body.status.status)) {
      window.clearInterval(timer);
    }
  }, 1500);
}

```

Final review uses only final artifacts from the run.

```text
manifest.finalResult
manifest.validationReport
manifest.qualityReview
```

Artifact route example:

```ts
// apps/web/src/app/api/screen-inference/runs/[runId]/artifacts/[artifactName]/route.ts
import { readFile } from "node:fs/promises";
import path from "node:path";
import { NextResponse } from "next/server";

const ALLOWED_ARTIFACTS = new Set([
  "final-result.json",
  "validation-report.json",
  "quality-review.json",
  "pipeline-result.json",
]);

type RouteContext = {
  params: Promise<{ artifactName: string; runId: string }>;
};

export async function GET(_request: Request, context: RouteContext) {
  const { artifactName, runId } = await context.params;
  if (!ALLOWED_ARTIFACTS.has(artifactName)) {
    return NextResponse.json({ error: "Artifact is not allowed." }, { status: 403 });
  }

  const filePath = path.join(
    process.cwd(),
    "data/runs/screen-generation",
    runId,
    "artifacts",
    artifactName,
  );

  return NextResponse.json(JSON.parse(await readFile(filePath, "utf8")));
}
```

Rerun should create a new run instead of resuming the Claude session in the MVP.

```ts
type RerunRequest = {
  previousRunId: string;
  source: { path: string };
  userFeedback?: string;
};
```

The rerun route can call the same `POST /api/screen-inference/runs` path with a new `runId` and tags such as `["web-new-screen", "rerun"]`.

### Phase D - MVP Approved DB Apply

MVP apply should be a dedicated route. It should not reuse `PUT /api/screens/:screenId/tree`, because that endpoint updates an existing screen tree.

Route shape:

```ts
// apps/web/src/app/api/screen-inference/runs/[runId]/apply/route.ts
import { readFile } from "node:fs/promises";
import path from "node:path";
import { validateRenderTree } from "@cx/validation";
import { NextResponse } from "next/server";
```
