## 2026-05-22 - 알아둘 것: type 스키마 혼탁

- 발견: 현재 `WireframeNode.type`이 두 가지 이질적인 개념을 한 필드에 섞어 담고 있음
  - **Leaf 컴포넌트 식별자**: `Button`, `ListText`, `AppBar` 등 카탈로그 entry와 1:1
  - **구조적 노드 식별자**: `page-stack`, `area.static`, `area.dynamic`, `layout-flex`, `layout-grid` — 카탈로그에 없고 렌더 트리의 구조 자체
- 결과: 카탈로그 기반 dispatcher로 전환하려고 보면 type lookup 결과에 세 갈래가 생김 — (1) 카탈로그 hit + 공급 hit, (2) 카탈로그 hit + 공급 miss, (3) 카탈로그 miss(=구조적 노드). (3)을 구분하는 신호가 type 문자열 패턴(`.` 포함, `page-stack` 등)에 묻혀 있어 dispatch에 ad-hoc 분기가 필요해짐
- 영향: "카탈로그는 계약, 패키지는 공급, 렌더러는 중계" 모델로 깔끔히 가려면 구조적 노드를 type이 아닌 다른 축(예: `node.kind` 또는 `node.role: "structural" | "component"`)으로 분리해야 함
- 진행 방향(미정): leaf vs structural 노드 모델링을 분리한 뒤 dispatcher 리팩토링 재개. 본 세션에서는 dispatcher 구현 직전에 정지
- 관련 변경: `database/tables/areas.json` 의 `ogn-mbr-term-list.pattern.id`를 `accordion-list`로 전환(테이블 레이어만 작업), `component-catalog.ts`의 `kind` 필드 주석을 "분기 신호 → 그룹 태그"로 격하

## 2026-05-22 - 다음 세션 후보: WireframeNode 폐기 검토

- 발견: 위 type 스키마 혼탁의 근원이 `WireframeNode` 중간층 자체일 가능성이 큼. DB 테이블은 leaf(`components.json`)와 structural(`areas.json`, region/screen)을 **테이블 단위로 분리**해서 갖고 있는데, `tables-to-render-tree.ts` 어댑터가 둘을 한 트리 한 `type` 필드로 합치면서 다형성이 발생함
- WireframeNode가 현재 하는 일:
  1. composite ref → nested children 풀기
  2. pattern.id → layout props 머지
  3. type → kind 계산
  4. display.when / hooks / bindings 해석
- 가설: 위 1~4가 모두 렌더 시점에 DB 테이블을 직접 워킹하면서 처리 가능. 즉 WireframeNode는 "정규화된 중간 표현"이지만 정규화의 이득이 비용보다 크지 않을 수 있음
- 폐기 시 도미노 정리: `WireframeNode` 스키마, `tables-to-render-tree.ts`, `runtime.ts`의 kind 매핑/`EXTRA_KIND_MAPPINGS`, kind union, 관련 테스트 — 통째로 사라지거나 단순화
- 비용: 렌더러가 DB 형태(composite ref, area children, pattern.id)를 직접 해석하도록 재설계. 카탈로그/패턴 스토어를 렌더 시점에 함께 조회
- 작업 순서 제안: type 스키마 분리와 WireframeNode 폐기를 **같은 작업의 두 면**으로 보고 통합 진행. 분리해서 풀면 변환 코드를 두 번 만지게 됨
- 다음 세션 시작점: `adapters/tables-to-render-tree.ts`를 읽고 어떤 정규화가 진짜 필요한지부터 식별
